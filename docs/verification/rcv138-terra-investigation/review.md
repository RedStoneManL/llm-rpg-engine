# RCV138 原生调查短局

普通非 demo `build_dashboard` 和默认 `GroundedAuthorStrategy`，四个连续玩家回合均实际发布。合成起点已接取“找到账簿的存放处”，客栈旧柜为第一调查点。没有预置第二条路线或证据。

1. 查证旧柜：原生作者写柜内无账簿、收条指向集市寄存簿，并提交 clue 和 follow_up。面板显示“有线索，待核实”，新增可前往集市路线。
2. 冷重开后路线保留，`open_source` 实际打开旧柜现场原文；玩家走到集市，面板提供就地查证行动。
3. 查证寄存簿：原生作者生成“寄存簿写明旧账簿寄存在七号柜。”并标 confirmed；独立语义判断请求与原生响应判其回答调查问题。面板显示“有可核验的证据”；通过 `open_source` 实际打开该原文。
4. 玩家要求按原文结案；作者实际引用现场观察 ID 和精确原文，独立语义判断认可、正文审稿认可，实际 `quest_resolved` 引用与正证据完全一致。冷重开后已结任务仍显示。正文明确没有拿到实体账簿；本局调查问题是存放处，不是取回。

完整生产作者、语义判断、正文审稿请求与逐份生成的 Terra 原生响应分别保存在 `requests.json`、`responses.json`；`progress.json` 是每回合发布后的 GUI 返回及打开原文结果；`verification.json` 保存冷重开状态、现场事件和结案事件；`synthetic-events.db` 是实际合成 SQLite 备份。证据来源、内容由本次原生作者生成，并非对预存真相的独立核实；语义判断同样由 Terra 依据请求原文给出，是模型样本，不证明其他模型或开放任务的稳定性。没有真实 HTTP 运输。

驱动 `probe.py` 每次处理当前动作，遇到未回答的请求时暂停，原样比对同一持久 SQLite 会话产生的请求；每个请求生成后追加响应，再运行下一步。现有原始数据含随机事件 ID，故不应在另一个新会话把旧响应当作重放成功。合成种子使用 demo 世界初始化函数，实际游戏入口为非 demo。为控制无关模型调用，关闭 digest_fleet、run_director、run_cascade、run_catchup、run_density、_run_demote_on_leave、run_lore；未覆盖这些后台功能。
